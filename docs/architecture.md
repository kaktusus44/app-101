# Базовая архитектура App 101

## Исходные допущения

- Предметная область и точные границы MVP будут уточняться по экранам оригинального приложения.
- На старте важнее скорость проверки сценариев, чем независимое масштабирование частей системы.
- Бизнес-модули должны быть отделены друг от друга, даже если backend разворачивается одним приложением.

## Компоненты MVP

### Frontend

- React + TypeScript.
- Vite для сборки и локальной разработки.
- React Router для маршрутизации.
- TanStack Query для серверного состояния.
- UI-kit выбирается после анализа экранов 101.

### Backend

- Go.
- Модульный монолит с разделением по бизнес-возможностям.
- REST API с контрактом OpenAPI.
- Единая точка входа, централизованные авторизация, валидация, аудит и обработка ошибок.

Предварительные технические модули:

- `auth` — аутентификация и сессии;
- `users` — пользователи;
- `access` — роли и права;
- `audit` — журнал значимых действий.

Предметные модули будут названы после разбора страниц и сценариев.

### Данные

- PostgreSQL как основное хранилище.
- Версионируемые миграции схемы.
- S3-совместимое хранилище только при наличии файлов.
- Redis и очередь задач только при появлении подтверждённых асинхронных процессов.

Первая серверная схема содержит `organizations`, `users`, `organization_members`,
`sessions` и `invitations`. Роль хранится в связи пользователя с организацией и
проверяется API, а не интерфейсом. Пароли и токены сессий/приглашений в открытом виде
в PostgreSQL не сохраняются.

### Развёртывание

- Docker Compose для локальной разработки и первого окружения.
- Reverse proxy с HTTPS.
- Структурированные логи, health checks и базовые метрики с первого релиза.

Текущий `docker-compose.yml` поднимает три сервиса: статический React frontend через
Nginx, Go API и PostgreSQL с постоянным volume. Nginx проксирует `/api` в backend,
поэтому HttpOnly-cookie остаётся same-origin.

## Правила границ модулей

- Модуль владеет своей бизнес-логикой и таблицами.
- Другие модули не обращаются напрямую к его внутренним пакетам.
- Взаимодействие идёт через явно определённые интерфейсы.
- Общий код ограничивается инфраструктурными примитивами и не содержит предметной логики.

## Путь развития

1. Реализовать MVP модульным монолитом.
2. Измерить реальные нагрузки и частоту изменений.
3. Добавить фоновые workers при появлении долгих операций.
4. Выносить модуль в отдельный сервис только при независимой нагрузке, отдельной команде, требованиях доступности или изоляции данных.
